# EasySatSim

![EasySatSim logo](resource/logo_doc.png)

EasySatSim is an extensible experimental platform for Low Earth Orbit (LEO) satellite network research. It is mainly intended for constructing LEO satellite network experimental environments on personal computing devices. The simulation process is organized around three core component types: **Entities**, **Behaviors**, and the **Protocol Stack**. The platform uses five architectural layers, namely the Controller Layer, Manager Layer, Execution Layer, Global Services Layer, and API Support Layer, to support scenario creation, component registration, entity execution, shared state maintenance, and extension interface management.

In the default implementation, EasySatSim can construct LEO constellations, ground users, user access, packet forwarding, routing, protocol stack processing, and network performance statistics. The default communication process uses an internal five layer protocol stack with packets as the basic processing unit. The network layer performs next hop selection, the link layer performs address mapping, and the physical layer estimates propagation delay, Doppler effects, path loss, and related factors.

EasySatSim provides extension interfaces through explicit registration and binding relationships. Within the current architecture and interface conventions, researchers can add or replace behaviors, protocol processing functions, routing algorithms, experimental metrics, and local scenario configurations. The repository includes three complete case studies and a Scapy based standard IPv4/UDP protocol integration example to demonstrate how these extension interfaces are used.

> **Modeling Scope**
> EasySatSim currently focuses mainly on LEO satellite network research. The default scenario uses a single layer, multi plane, circular orbit Walker Delta constellation. Requirements such as high precision orbital dynamics, waveform level communication processing, and external routing daemons require further extension of EasySatSim or integration with specialized tools.

## Main Features

- Configurable LEO satellite constellations and ground user populations. The default scenario uses a single layer circular orbit Walker Delta constellation and supports configuration of the number of orbital planes, satellites per plane, orbital altitude, inclination, phase, number of users, user distribution, and traffic rate.
- Packet transmission between users and satellites and among satellites, including user access, buffer queuing, hop by hop forwarding, routing decisions, link layer address mapping, destination delivery, and packet loss recording.
- A default five layer protocol stack consisting of the application, transport, network, data link, and physical layers. Within the existing layer structure, researchers can register or replace protocol data types, encapsulation and parsing functions, and their mappings.
- Active, passive, and common behaviors. Active behaviors are used for periodic tasks, passive behaviors are triggered by packet arrivals, and common behaviors are used for shared state updates of entity clusters such as constellations.
- Qt based interactive visualization, including 3D and 2D scenario views, object information, network performance metrics, runtime logs, screenshots, and result export.
- Timestamped CSV output by default. Each case study separately maintains experiment logs, processed metrics, and plotting results.
- Case study tutorials explaining how to add research specific logic on top of EasySatSim's existing scenarios, entities, behaviors, and protocol stack.

## Runtime Environment

The current open source release has been verified on Windows using CPython 3.13.12. Other Python versions and operating systems may also work, but dependencies, visualization, and simulation results should be revalidated before they are used for formal experiments.

The main program uses the following primary dependencies:

- NumPy
- Numba
- Colorama
- Pillow
- PyQt5
- VisPy
- PyQtGraph

Install the main runtime dependencies with:

```powershell
python -m pip install -r requirements.txt
```

Install additional dependencies according to the intended workflow:

```powershell
# Common result processing and plotting
python -m pip install -r requirements-plotting.txt

# Three complete case studies
python -m pip install -r cases/case1/requirements.txt
python -m pip install -r cases/case2/requirements.txt
python -m pip install -r cases/case3/requirements.txt

# Tests and installation diagnostics
python -m pip install -r tests/requirements-test.txt
```

Case 1 requires TensorFlow. Case 2 requires PyTorch, torchvision, and the CIFAR-10 dataset used by the case. Case 3 uses pandas and Matplotlib for evaluation and plotting. Dependencies for the IPv4/UDP example are listed in `examples/protocol_ipv4_example/requirements.txt`.

On the first Case 2 run, CIFAR-10 is downloaded by torchvision. The dataset is not bundled with the EasySatSim source code. Git ignores the downloaded archive and extracted directory. See the [Case 2 data guide](cases/case2/experiment/data/README.md) for the data source, checksums, local verification, and offline use instructions.

Before running a complete case study, we recommend reading its corresponding `TUTORIAL.md`.

## Run the Default Simulation

The current release uses a complete Starlink Phase I A scenario as its default configuration. It contains 32 orbital planes with 50 satellites per plane, for a total of 1,600 satellites and 500 users. Its initialization and live update overhead is therefore higher than that of the diagnostic configuration described above, and actual runtime performance depends on the host hardware.

After installation verification succeeds, run the simulator from the repository root:

```powershell
python -m src.main
```

The EasySatSim window first displays the active configuration. Before starting the simulation, you can inspect the constellation parameters, user count, network step, physical layer state, configuration file, and output path, then select `Simulation > Start Simulation`.

Opening the window alone does not start the simulation worker processes. After selecting Start, wait for scenario initialization. The Run Log can be used to distinguish normal initialization from an actual error.

During a run, the interface provides:

- `3D View`: displays the three dimensional constellation and user access relationships;
- `2D View`: displays satellite ground tracks and user access relationships;
- `Object Details`: displays the scenario overview and allows detailed inspection of satellites or users selected in the 2D View;
- `Performance Metrics`: displays live network performance metrics;
- `Results`: provides result export, packaging, screenshots, and access to the output directory.

Default parameters are stored in `configuration/simulation_config.py`, and the reference configuration is stored in `configuration/simulation_config.default.py`. Timestamped results from the default simulation are written to `output/`.

## Performance Benchmark Reported in the Paper

The scalability benchmark reported in the paper was conducted on a personal computer equipped with an Intel(R) Core(TM) i5-14600KF CPU and 32 GB of RAM. The test establishes one way communication between two users located in Beijing and Tokyo and uses whether the receiver can continuously receive the data generated by the sender as the runtime criterion.

Under this hardware configuration, traffic load, and runtime criterion:

- the 400 satellite scenario takes approximately 2.1 s to create, with CPU utilization of approximately 3.4%;
- at 10,000 satellites, memory utilization is approximately 37.4%, and the continuous reception criterion is still satisfied;
- the 12,800 satellite scenario can still be created and run, but memory utilization reaches approximately 53.2%, and the receiver can no longer continuously satisfy the above runtime criterion.

Therefore, the result reported in the paper only shows that, under the specified hardware, traffic load, and runtime conditions, the 10,000 satellite configuration satisfies the continuous reception requirement. It should not be interpreted as a general scale limit independent of hardware, traffic, or protocol configuration.

## Extension Model

A typical EasySatSim scenario is constructed in the following sequence:

```python
from src.simulation.controller.scene_controller import SceneController

scene = SceneController()
scene.create_scene()
scene.default_behavior()
scene.default_stack()

# Register case specific behaviors, protocols, routing, or metrics here.

scene.configuration_complete()
scene.run_simulation(plotter=True)
```

`scene.create_scene()`, `scene.default_behavior()`, and `scene.default_stack()` first load EasySatSim's existing scenario, default behaviors, and default protocol stack. Researchers can then add case specific components through the corresponding managers and registration interfaces before `configuration_complete()`.

Common extensions supported within the current interfaces include:

- Replacing routing algorithms: a new next hop decision function can usually be integrated through the routing registration interface during initialization.
- Adding protocol types within an existing protocol layer: define protocol data structures, serialization and deserialization logic, and encapsulation and parsing functions, then establish the mappings among protocol identifiers, data types, and processing functions.
- Adding new entity behaviors: register active, passive, or common behaviors and bind them to selected entities or entity clusters.
- Adding case specific entities or states: these can be implemented in local case code, but extensions that introduce new shared state across processes, lifecycle logic, or cross layer interaction also require corresponding changes to data structures and initialization logic.

Note that **adding a new protocol layer, changing the existing protocol layer order, or directly integrating an unmodified operating system protocol stack cannot be completed solely through the current registration interfaces**. These requirements require changes to the protocol stack core or additional external adaptation mechanisms.

The three directories under `cases/` demonstrate how scenario specific logic can be kept inside the case directory while continuing to reuse the general satellite network functionality in `src/`.

## IPv4/UDP Protocol Integration Example

`examples/protocol_ipv4_example` demonstrates how standard network protocol packets can be integrated into the EasySatSim simulation protocol stack through the existing protocol registration mechanism.

The example uses Scapy to construct and parse standards formatted IPv4/UDP packet bytes. EasySatSim continues to provide the satellite network functions and performs destination address checks, per hop TTL updates, and IPv4 header checksum recalculation at the network layer. This example demonstrates that **standards formatted IPv4/UDP packets and selected protocol processing logic can be executed inside EasySatSim**.

Run the example with:

```powershell
python -m pip install -r examples/protocol_ipv4_example/requirements.txt
python examples/protocol_ipv4_example/main.py
python examples/protocol_ipv4_example/show_result.py
```

The protocol example outputs hop by hop processing evidence and PCAP files that can be used to inspect IPv4/UDP fields, TTL changes, and header checksum updates. See the [IPv4 example tutorial](examples/protocol_ipv4_example/TUTORIAL.md) for implementation and validation details.

## Results and Reproducibility

- The default simulation writes timestamped CSV results to `output/`.
- Each case study stores raw results, event logs, processed metrics, and paper figures under its own `experiment/` and `plotting/` directories.
- Each case configuration is stored independently under `cases/<case>/src/configuration/`, without modifying the global default configuration.
- The individual case tutorials document random seeds, experiment modes, execution order, result processing, and plotting steps.
- The IPv4/UDP example provides an independent validator and PCAP output for checking key field processing during multi hop forwarding of standard protocol packets.

Lightweight checks, installation diagnostics, and short tests are intended to confirm that the environment and code paths are working. They should not be used directly as the final experimental results reported in the paper. Paper figures and final metrics should be generated using the complete experimental configurations documented in the corresponding case tutorials.
